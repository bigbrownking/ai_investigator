# AI Investigator — backend

Java/Spring Boot API для работы с делами и их материалами. Приложение хранит дела, файлы, участников и историю действий; помогает готовить планы и документы; обрабатывает материалы осмотра и допросов. Часть операций использует отдельные AI-сервисы и асинхронные очереди. В этом репозитории находится backend, фронтенда здесь нет.

## Что умеет приложение

| Область | Возможности |
| --- | --- |
| Дела и материалы | Создание и поиск дел, изменение статуса и языка, загрузка и скачивание файлов, порядок файлов, тома, история статусов, участники и фигуранты. |
| Доступ | Выдача и отзыв доступа к делу, управление правами на файлы, роли пользователей и разграничение административных операций. |
| Анализ дела | Чат по материалам дела, просмотр истории сообщений, построение дерева данных по модулям, обновление результатов анализа. Ответы чата передаются потоком через SSE. |
| Процессуальные документы | Генерация и редактирование разделов квалификации и обвинительного документа, переформулирование фрагментов и выгрузка результатов. |
| Планы | Генерация плана, работа с действиями и их статусами, отправка на согласование, утверждение, отклонение, история правок и уведомления. |
| Допросы | Создание допросов, протокол и вопросы/ответы, аудиофайлы, контроль времени и перерывов, чат, выгрузка документа. |
| Осмотр и отчёты | Загрузка материалов осмотра, обработка и распределение фрагментов, скачивание результатов, генерация отчёта по делу. |
| Администрирование | Пользователи, роли, обращения, статистика, журнал действий, управление владельцами и статусами дел. Региональным администраторам доступны отдельные операции. |
| Зональная отчётность | Шаблоны форм, заполнение и отправка строк, просмотр отправленных форм, сводный отчёт и экспорт. |
| Прочее | Регистрация и вход, JWT, сброс пароля, настройки профиля, справочники, обратная связь и интеграция с сервисом FaceAuth. |

Наличие API не означает, что каждая функция работает автономно: анализ, генерация текстов, распознавание и проверка лица зависят от внешних сервисов.

### Что делает ИИ, а что делает backend

ИИ-модели не находятся в этом репозитории. Backend обращается к внешним сервисам для генерации квалификации, обвинительного документа и плана; чата по делу; построения дерева материалов; подготовки вопросов для допроса, поиска противоречий, переформулирования вопросов и очистки расшифровки; обработки осмотра и создания справки. Загрузка материалов также запускает асинхронную обработку через очереди. Результат приходит в виде текста, JSON или готового файла — в зависимости от операции.

Backend проверяет пользователя и права, собирает параметры запроса, отправляет их внешнему сервису, сохраняет результат и позволяет человеку просмотреть и изменить его. Часть полей backend заполняет сам: например, в плане он подставляет текущую дату, исполнителя из дела и вычисляет срок действия по числу дней, которое вернул сервис.

Файлы Word для квалификации, обвинительного документа и плана формирует сам backend из сохранённых разделов и данных плана с помощью Apache POI. Протокол допроса также собирается backend по шаблонам для языка и роли участника. Для справки есть иной путь: внешний сервис возвращает готовый файл, а backend сохраняет его в MinIO и отдаёт пользователю. Поэтому «ИИ формирует документ» здесь обычно означает, что ИИ предлагает **содержание**, а backend создаёт `.docx`, заполняет служебные поля и управляет сохранением и скачиванием.

## Основные группы API

- `/auth`, `/users` — учётная запись и профиль.
- `/cases`, `/cases/{caseId}/access/{userId}` — дела, материалы, участники и доступ.
- `/cases/chat`, `/chat`, `/tree` — чат и анализ материалов.
- `/cases/qualification`, `/cases/indictment`, `/cases/plan` — документы и планы.
- `/cases/{caseId}/interrogations`, `/cases/{caseNumber}/osmotr`, `/cases/{caseNumber}/report` — допросы, осмотр и отчёты.
- `/admin`, `/reg-admin`, `/zonal`, `/admin/zonal` — администрирование и зональная отчётность.
- `/dict`, `/feedback`, `/face-id` — справочники, обратная связь и FaceAuth.

Полный список методов и параметры доступны в Swagger UI после запуска: `http://localhost:5556/swagger-ui/index.html` при `PORT=5556`. Большинство методов требует JWT; права дополнительно проверяются по роли и доступу к делу.

## Роли пользователей и расположение кода

Роль — запись в таблице `roles`, связанная с пользователем из таблицы `users`. Определение сущностей находится в `src/main/java/org/di/digital/model/user/Role.java` и `User.java`. Это строки в БД, а не отдельные классы или директории для каждой роли.

| Роль | Общее назначение | Где смотреть код |
| --- | --- | --- |
| `USER` | Обычный пользователь. Работает с делами и модулями, на которые ему предоставлен доступ. | Регистрация: `service/impl/auth/AuthServiceImpl.java`; API дел: `controller/CaseController.java`; права на конкретное дело: `service/impl/cases/access/CaseAccessServiceImpl.java`. |
| `ADVANCED_USER` | Пользователь с расширенными управленческими операциями, в том числе в согласовании планов. | Назначение роли: `service/impl/admin/AdminServiceImpl.java`; проверки плана: `controller/CasePlanController.java`; часть регионального API: `controller/RegAdminController.java`. |
| `ZONAL` | Заполнение зональных форм и работа с доступными региональными данными. | API форм: `controller/ZonalTableController.java`; условия доступа: `security/zonal/ReportingAccess.java`; назначение роли: `service/impl/admin/AdminServiceImpl.java` и `RegAdminServiceImpl.java`. |
| `REG_ADMIN` | Региональное администрирование пользователей и дел; часть прав зависит от региона и должности. | API: `controller/RegAdminController.java`; логика: `service/impl/admin/RegAdminServiceImpl.java`; дополнительные проверки: `security/zonal/ReportingAccess.java`. |
| `ADMIN` | Общесистемное администрирование пользователей, ролей, дел и статистики. | API: `controller/AdminController.java`; логика: `service/impl/admin/AdminServiceImpl.java`; маршрутные ограничения: `config/WebConfig.java`. |

Все указанные пути в таблице начинаются с `src/main/java/org/di/digital/`. Общие проверки JWT и маршрутных прав находятся в `security/jwt/JwtRequestFilter.java`, `security/UserDetailsImpl.java` и `config/WebConfig.java`. Дополнительно методы проверяют роль через `@PreAuthorize`, а доступ к конкретному делу — через сервис прав. Поэтому наличие роли само по себе не даёт доступа ко всем делам.

Обычная регистрация `/auth/signup` создаёт пользователя с ролью `USER` в неактивном состоянии и заявку на одобрение. Роли `ADVANCED_USER`, `ZONAL` и `REG_ADMIN` назначаются через административную логику. В репозитории нет готовых логинов/паролей и скрипта заполнения таблицы `roles`; список существующих пользователей зависит от подключённой PostgreSQL.

Отдельно: `model/enums/cases/MessageRole.java` описывает роли сообщений чата, а `model/enums/dictionary/InterrogationRole.java` — роли участников допроса. Они **не являются** ролями доступа пользователей.

В `controller/AuthController.java` есть `/auth/SIGNUP`, который вызывает создание `ADMIN`. В `config/WebConfig.java` для этого маршрута требуется аутентификация, но не проверяется роль администратора. Этот маршрут требует отдельной проверки безопасности перед развёртыванием.

## Технологии и данные

- Java 17, Spring Boot 4, Maven, Spring Security/JWT, JPA.
- PostgreSQL — основные данные приложения. Для локальной конфигурации также предусмотрена отдельная FL-база в ClickHouse.
- MongoDB — очередь задач; RabbitMQ — обмен заданиями и результатами обработки.
- Redis — временные данные и события; MinIO — файлы.
- Внешние AI-сервисы задаются через `MODEL_HOST` и порты в `.env`; FaceAuth — через `FACEAUTH_BASE_URL`.
- SSE и WebSocket применяются для потоковых ответов и событий.

При запуске Hibernate использует `ddl-auto=update` для основной PostgreSQL. Отдельной системы миграций Flyway/Liquibase в репозитории нет. Некоторые сервисы переноса данных существуют в коде; автоматическую миграцию шифрования файлов регулирует `MINIO_ENC_MIGRATE_ON_STARTUP`.

## Локальный запуск

1. Установите JDK 17.
2. Настройте `.env` в корне репозитория. Он исключён из Git; требуемые переменные перечислены в `src/main/resources/application.properties`.
3. Поднимите отдельно PostgreSQL, ClickHouse, MongoDB, Redis, RabbitMQ и MinIO по адресам из `.env`.
4. Установите Maven и запустите backend: `mvn spring-boot:run`. Скрипт `mvnw.cmd` присутствует, но необходимые файлы `.mvn/wrapper` в репозитории отсутствуют.
5. Проверьте `http://localhost:5556/actuator/health`, если в `.env` установлен `PORT=5556`.

В репозитории сейчас нет Compose-файла для этих сервисов. Для полноценного старта нужен доступный MinIO и RSA-ключ по пути `RSA_PRIVATE_KEY_PATH`. FL-база требует таблиц и данных, которых в репозитории нет. AI-сервисы и FaceAuth также не входят в него; без них соответствующие функции недоступны. SMTP-адрес задан в `application.properties` и требует отдельного сервера.

## Проверка и разработка

После запуска проверяйте API через Swagger UI и используйте тестовые данные: приложение может изменять схему PostgreSQL, создавать bucket в MinIO и выполнять фоновые задачи. Автоматических тестов в `src/test` сейчас нет; `mvn test` не заменяет функциональную проверку API и интеграций.
